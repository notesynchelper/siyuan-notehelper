## 问题一：微信消息没按时间合并，顺序混乱 —— ✅ 已复现（确定性）

用他真实数据一跑就中。2026-08-17 那天他有 8 条消息，合并文档里的实际顺序是：

| 文档中的顺序 | 时间戳 | 应有顺序 |
|---|---|---|
| 1 | 18:19:50 | 10:28:50 |
| 2 | 22:21:55 | 11:04:02 |
| 3 | 15:28:25 | 12:03:23 |
| 4 | 10:28:50 | 14:52:05 |
| 5 | 11:04:02 | 15:28:20 |
| 6 | 12:03:23 | 15:28:25 |
| 7 | 14:52:05 | 18:19:50 |
| 8 | 15:28:20 | 22:21:55 |

### 根因：排序只在「一页」之内，而分页是倒序的

1. 服务端 `search` 按 **`updated_at DESC, id DESC`** 返回（`omniserver/database.js:574`），即**最新的在前**。
2. `syncManager.sync()` 每页拉 **15 篇**（`src/sync/syncManager.ts:114`），逐页处理。
3. `fileHandler.processArticleBatch()`（`src/sync/fileHandler.ts:119`）只对**本页**内的消息
   分组 + `sortArticlesByTime` 排序（`:167`）。
4. `mergeToExistingDocument()` 永远**追加到文档末尾**（`src/sync/fileHandler.ts:439`
   `existingContent + separator + newContentPart`），没有按时间插入。

脚本现在**直接记录每页的真实构成**（不再是事后推断，codex 复检 #1），实测：

```
page 1: 15 items, 2 条消息 -> 22:21:55, 18:19:50
page 2: 15 items, 1 条消息 -> 15:28:25
page 3: 15 items, 11 条消息 -> 15:28:20, 14:52:05, 12:03:23, 11:04:02, 10:28:50, …
page 4:  8 items, 1 条消息 -> 19:57:37
```

每页内部升序、页与页之间倒序拼接，正好得到观察到的那个序列。

⚠️ **复检修正**：原稿写「只要跨页必然乱序」是过强了。跨页只是**必要条件**——还要前一页
某条消息的 `savedAt` 晚于后一页某条，ASC 拼接才会乱。真正的问题是
**服务端按 `updated_at` 分页、插件按 `savedAt` 排序**，两者不一致 ⇒ 页间顺序根本没有保证。
在他这份数据分布下是确定乱序。

### 修复方向

- 治标：把「按目标文件分组 + 排序」从 per-batch 提到 **整轮同步收集完再写**，或
- 治本：合并写入时按时间戳**插入**而不是无脑 append（也能修好跨轮同步、跨设备的乱序），
- 另有一处不一致：排序用的是 `savedAt`，而服务端分页用的是 `updated_at`。

## 问题一b：删掉合并的消息后重新同步不会再生成 —— ✅ 已复现（根因已改正）

⚠️ **复检修正**：原稿归因为「游标越过 + 索引 2 秒延迟两层叠加」，codex 指出这站不住
（脚本删除后已 `settle()` 等索引稳定，仍不重建，说明游标一条就够；而且脚本用的
`syncTimeOffset: 0` 并不是默认值 12 小时）。按用户原话「删除**这条**合并的消息」重做实验后，
真正的根因是另一个、且严重得多的问题。

### 真根因：`custom-merged-ids` 从不与正文对账

合并模式把「这篇已经并进来了」记在**文档级**属性 `custom-merged-ids` 里。用户在合并文档里
删掉**其中一条消息**（一个块），这个列表**不会**跟着变。实测（`repro-merged-message-deleted.js`，
用默认 `syncTimeOffset=12`）：

```
merged doc 同步助手_2026-08-17: 8 messages, merged-ids=8
deleted ONE message block "📅 2026-08-17 15:28:20"
   now: 7 messages in doc, merged-ids still = 8
   sync again (cursor advanced): {"count":0,"skipped":1}    -> 没回来
   sync again (cursor RESET):    {"count":0,"skipped":53}   -> 全量重拉，还是没回来
   after reset+resync: 7 messages
>>> deleted single message restored? NO — 永远回不来
```

**即使「重置同步时间」全量重拉 53 篇，也是 53 篇全 skip** —— 那条消息永久不可恢复。
这与用户原话「删除这条合并的消息，再重新同步，也不会重新生成这条消息」完全吻合。

（删掉**整篇**合并文档则是另一回事：那属性跟着文档一起没了，只要文章还落在拉取窗口内
就会重建；默认 12 小时回溯窗口之外的就拉不到了，这是游标设计使然，不是 bug。）

## 问题二：「重建索引」是不是重复同步的元凶 —— ❌ 本次实验未复现（结论已降级）

做了 A/B：同一份数据、同一个全量窗口重新同步两次。

| 场景 | 结果 |
|---|---|
| 索引正常 | `created=0, skipped=53`，文档数 52→52，**零重复** |
| `rebuildDataIndex` 期间同步 | `created=0, skipped=53`，文档数 52→52，**零重复** |

重建索引确实会让索引短暂**全空**（实测 t+162ms 时 `docs=0 / source-id=0 / merged-ids=0`），
但在 52 篇的库上整个重建只要 **~0.46s**。

⚠️ **复检修正**：原稿解释成「插件第一步走网络，等它写盘时索引已恢复」，这是错的——
`sync()` 的第一件事就是 `IdIndex.build()`（`syncManager.ts:71`），**在任何网络请求之前**。
而且 `skipped=53` 并不能说明是哪一层去重生效：`IdIndex` 空了，后面的路径去重
（`getDocumentByPath` → `getIDsByHPath`）照样能命中。

所以这条结论只能**降级**为：**在 52 篇、该时序下没有观察到重复**，不足以断言大库上也安全
（几千上万篇的库重建要几分钟，空窗大得多）。可以回复用户的是「重建索引不是你这次重复的
直接原因」，但不能说「重建索引一定不会导致重复」。要坐实还需要故障注入，把
`IdIndex.build()` 和每次最终去重判断都强制压在空索引期内。

### 「点了升级插件导致同步卡死」——未复现，但代码层有确定的风险点

无头环境驱动不了 Electron UI，这条**没有复现**。代码层能确认的事实：

- 插件设置页有「立即更新」按钮 → `performUpdate()`（`src/updater.ts:137`），
  它**不检查是否正在同步**，会在插件运行中直接覆写 `/data/plugins/siyuan-notehelper/index.js`。
- `checkAndUpdate()` 在**每次同步开头**都会跑一次（`src/sync/syncManager.ts:36`，fire-and-forget）。
  若此时用户又在集市点「升级」，两条路径会并发写同一批文件。
- `onunload()`（`src/index.ts:397`）会停定时器、拆 UI，但**不会中断正在飞的 `sync()`**。
  旧实例会继续跑完并调用旧的 `saveSettings()`，可能把游标写回、盖掉新实例的状态。
- `settings.syncing` 会被持久化成 `true`（`src/index.ts:345-349` 的注释已记录此事），
  靠 onload 里 `await loadSettings()` 之后手动清零兜底。

建议：`performUpdate()` 与集市升级前先挡住/等待正在进行的同步，并给 `sync()` 一个可取消的信号。

## 问题三：插件启动同步与思源同步撞车 → 文章重复 —— ✅ 机制已复现（竞争对手已改正）

### 先排除一个猜测：不是「索引没建好」

造了一个 **2072 篇文档**的库重启内核实测：

- 内核 `bootProgress=100` 用时 **806ms**
- 插件的 `syncOnStart` 在 **t+10s** 触发，此时 `docs=2073/2072、source-id=38/38、merged-ids=6/6`
  —— **索引早就完整了**，同步结果 `created=0, skipped=53`，零重复。

所以在**本机、这个规模**下，本地建索引不是瓶颈，10 秒延迟对它够用。

⚠️ **复检修正**：这不能外推成「索引因素可以排除」。单机单次计时说明不了移动端、慢盘、
加密库或上万篇库的情况；而且 `source-id=38/38` 只覆盖了带插件属性的那 38 篇，不是全部
2072 篇的去重状态。两个机制也不互斥——「下载没完成」成立，不代表「索引尚未可见」没有同时参与。

### ⚠️ 复检修正：竞争对手**不是**思源的「启动同步」

codex 复检指出，思源内核的启动顺序是 `BootSyncData()` → `InitBoxes()` → `SetBooted()`
（`kernel/main.go:42-47`，3.6.5 / 3.8.0 一致），而 `SetBooted()` 才把 `bootProgress` 置 100，
前端和插件都要等进度 100 才加载。**也就是说启动同步跑完之后插件才被加载，两者不可能相撞。**
原稿把它当成竞争对手是错的。

那用户看到的是什么？是**启动之后的另一次同步**——最可能是：

- **感知同步（Perception）**：`BootSyncData()` 里 `connectSyncWebSocket()` 建了长连接，
  别的设备一同步，这台就被推着同步（`sync.go:127-129`）。用户是多设备用户，这条最贴合他
  「插件同步了新文章过来，思源同步也同步了同一篇新文章过来」的描述；
- 定时同步（`setSyncInterval`）刚好在开机后不久触发；
- 启动同步失败后的重试。

这些**都发生在插件已经加载之后**，正好落在插件那 10 秒定时器的射程里。

### 真正的机制：文档**还没被下载下来**

设备 A 已经同步过文章 Y 并写出了 `Y.sy`，设备 B 上这次同步还没把 `Y.sy` 拉下来，
插件的 `syncOnStart` 就到点开跑了。
插件所有去重层（`IdIndex` / `getDocumentByPath` / `checkDocumentBySourceId`）查的都是
**本地**有没有这篇 —— 文件压根还没到，全部 miss，于是插件自己造了一份；
随后思源同步把 A 的那份也送达 → **同一篇文章两个文档**。

A/B 实测（`tests/real-siyuan/repro-boot-sync-race.js`）。⚠️ 这里的「云同步送达」是
**模拟**的：直接把 A 那份 `.sy` 拷进 B 的 `data/` 再重建索引，绕过了思源同步仓库的
版本比较/冲突处理/增量索引。所以它证明的是「**若文档以晚到的方式出现，本地去重无法预防
重复**」，不等于端到端验证了真实云同步的行为：

| 场景 | 插件同步结果 | 该文章最终文档数 |
|---|---|---|
| **插件先同步**，思源同步随后送达 | `created=1, skipped=52` | **2 份** ❌ 同路径同 source-id |
| **等这次同步完成**再同步（拟议修法） | `created=0, skipped=53` | **1 份** ✅ |

```
/笔记同步助手/2026-08-04/会议手册丨第六届全国木质素会议   (block 20260819163831-7oytc6c)  ← 插件造的
/笔记同步助手/2026-08-04/会议手册丨第六届全国木质素会议   (block 20260819163820-9v2utv2)  ← 思源同步送来的
```

### 现状：插件对思源的同步状态完全无感知

`src/index.ts:375-379`：

```ts
if (this.settings.syncOnStart && shouldRunSyncOnStart()) {
    setTimeout(() => { this.performSync(true); }, 10000); // 延长到10秒，让思源笔记先完成启动
}
```

全仓库 `src/` 下**没有任何一处**调用 `/api/sync/*`、订阅 `sync-start`/`sync-end`、
或读 `window.siyuan.config.sync` —— 固定 10 秒是唯一的保护。
（`docs/防重复优化方案.md` §六 把「思源刚启动时数据库未就绪」评为低风险、理由是
"已有 syncOnStart 延迟"；这次实测说明**真正的风险不在索引，而在下载**，那条延迟挡不住。）

### 修复方案（已实现）

思源 3.6.5 / 3.8.0 都会向**每个插件的 eventBus** 派发 `sync-start`(code 0) /
`sync-end`(code 1) / `sync-fail`(code 2)（`app/src/dialog/processSystem.ts:621-628`），
新增的 `src/sync/siyuanSyncGate.ts` 就靠它。判定规则同时要防「等不到」和「白等」：

| 情形 | 行为 |
|---|---|
| 思源没开云同步 | 立刻放行，一秒不等 |
| 静默期（25s）内没见到任何 sync 事件 | 放行 —— 覆盖「挂监听时同步早跑完了、事件拿不到」 |
| 见到 `sync-start` | 撤掉静默期，一直等到 `sync-end` / `sync-fail` |
| 超过 maxWait（5 分钟） | 强制放行 —— 绝不能因为等同步而永远不同步 |

`sync-fail` 也放行：同步失败后不会再有后续事件，继续等只会让插件永远不同步。
超时同样选择**放行而不是不同步**——漏同步是数据缺失（用户不知道自己少了东西），
重复只是数据冗余（看得见、可删），两害相权取轻。

配套还修了两个生命周期问题（codex 复检 #11 也点到）：启动同步的定时器现在存了句柄并在
`onunload()` 里清除（否则插件停用/重载后旧实例的定时器还会到点再同步一次，和新实例撞车）；
闸结算时必定取消全部订阅、只结算一次。

> 补充：只要「多设备 + 云同步」还在，这个竞态就不可能只靠本地去重根治
> （`docs/防重复优化方案.md` §二 场景 1 已有相同结论）。闸只能关掉「插件启动时**正好有一次
> 同步在飞**」这个窗口；文档在插件拉完之后才到达的一般情况，本地去重救不了，
> 那需要服务端/全局维度的去重。

一b 的对账**刻意偏保守**——凡是拿不准一律当作「还在」跳过，宁可某次恢复不了也绝不制造重复：

（同一秒两条消息，或格式只到日期）—— 都跳过。
但**正文是空串不算读取失败**：用户可能把整篇合并文档清空了，那种情况必须能恢复。

### 关键设计：锚点必须「存下来」，不能每次重新渲染

这是 codex 代码复检抓出的**批量重复**风险，也是本次改动里最关键的一处设计：

初版实现每次按当前 `dateSavedFormat` 重新渲染锚点去正文里找。问题是用户一旦改了时间格式，
新锚点跟历史正文全部对不上 → 所有还在的历史消息都被判成「已删除」→ **全部重新追加**，
那是一场比原 bug 严重得多的批量重复。

最终实现：追加消息时把它**真的写进正文的那段时间戳**存进文档属性 `custom-merged-anchors`
（id → 锚点文本），之后对账只拿存下来的那串字去找，与用户后来怎么改展示格式完全解耦。
唯一性也不再靠猜（初版用「长度 ≥ 10」判断区分度，而 `yyyy-MM-dd` 会让同一天所有消息撞车），
改成在存下来的锚点集合里实际数一遍，不唯一就不对账。

配套的其它安全闸：

1. **只存「确实出现在正文里」的锚点**。默认文章模板 `DEFAULT_TEMPLATE` 里没有 `dateSaved`，
   `MergeMode.ALL` 下普通文章正文根本不含时间戳 —— 这类锚点直接不存，对账对它们永远不生效，
   退回老的 skip 行为。真机 `MergeMode.ALL` 连续同步三轮验证：`count=0/0`、块数 1125→1125 不变。
2. **老文档天然免疫**。本次修复之前写入的文档没有 `custom-merged-anchors`，一律跳过对账，
   不会因为升级插件就批量重复。
3. **用户手改标题会被当成删除**。把某条消息的时间戳标题改掉但留着正文，对账会判定「被删」
   并重新追加一份。这是该语义的必然代价，方向仍是「宁可多一份也不丢」。
4. **推迟合并会把当轮消息全攒在内存里**。只攒合并类（消息体量小），普通文章仍逐页流式写；
   `MergeMode.ALL` + 大量长文时最坏一轮 1000 篇带正文驻留（offset 上限就是 1000）。
5. **分页中途失败时本轮消息一条都不写**（旧实现会写完已成功的页）。游标同样不前进，
   下轮整窗重拉，不丢数据，反而比「写一半」干净。

### 启动闸：监听必须在 onload 就挂上

同样是 codex 抓出的阻断项。初版是「10 秒定时器到点后才开始订阅 sync 事件」，
但思源的感知/定时同步完全可能在这 10 秒里就已经开跑——那时 `sync-start` 早发过了，
晚挂的监听收不到，闸会在静默期结束后误判成「没有同步要等」直接放行，照样撞车。
最终实现把订阅提到 onload 阶段（与 10 秒定时器同时起步），定时器到点后只是 `await` 那个已经
在监听的闸。
